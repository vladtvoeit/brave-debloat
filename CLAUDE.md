# brave-debloat

Two scripts that turn off Brave's crypto, ads, AI and telemetry — one for
macOS, one for Windows — and make the settings survive reboots and updates.

What each policy does and how to run the scripts is in [README.md](README.md);
it is not repeated here. This file records *why* the design is what it is, so
the same dead ends are not explored twice.

## Definition of done

This project stopped converging once "done" meant "no reviewer can find
anything". A reviewer told to find problems in ~2800 lines always can, and each
round of fixes added code whose own defects the next round then found: in the
last stretch most findings were in things added by the previous round. So done
is defined here, and the review loop stops by rule.

A change is done when:

1. `tools/check.sh` passes, and anything it SKIPs is named in the commit or in
   the review's first line.
2. Every behaviour the README promises is either covered by a check or listed
   under *Not verified* at the end of this file.
3. After the last change to a script, it has been run for real on its own OS.
   The Windows script is run by hand, since nothing here can run PowerShell.
4. One review pass reports no **blocking** finding.

**Blocking** means something a user running the documented commands on a
supported system can hit: a policy or setting with no effect or the opposite
effect; data loss, or a file left with the wrong owner or permissions; a message
or document that says something untrue; the primary layer (the policies)
failing silently.

**Not blocking**, and not fixed unless real use turns them up: conditions that
need an unusual setup (several users logged in at once, a profile path with
brackets in it, a file locked by another program), style, further hardening of
paths that already fail loudly, and anything in `tools/` that does not make a
check pass wrongly. They get one line in the review and are left alone.

Rounds: two per change. A third only if the second found a blocking defect in
code the first round's fix introduced. Nothing is added to `tools/` unless it
would have caught a defect that actually got through.

## Design decisions

- **macOS policies ship as a configuration profile, never as a plist written
  into `/Library/Managed Preferences/`.** That directory is generated by macOS
  from installed profiles, and a file placed there by hand is treated as stray
  and deleted — in practice at the next reboot, taking every policy with it.
  This is what made the original script appear to "stop working" over and
  over. A profile is the only durable route. Do not reintroduce a direct
  write, and do not add a LaunchAgent that rewrites the plist on a timer —
  that is a workaround for a problem that has a correct solution.
- **The macOS user-domain layer (`defaults write com.brave.Browser`) does not
  substitute for the profile, and barely helps at all.** Values written there
  are not `Forced`, so Chromium loads them at *recommended* level — and every
  Brave policy declares `can_be_recommended: false`, while the code paths
  (`brave_rewards::IsDisabledByPolicy` and friends) require
  `IsManagedPreference()`, which is false for recommended values. Rewards,
  Wallet, Leo and News are therefore **not** disabled by this layer. It is
  kept only for upstream Chromium policies that do accept the recommended
  level. The configuration profile is required, not optional — never present
  `--no-profile` as an equivalent route.
- **`HKCU\SOFTWARE\Policies` is writable only by administrators**, so
  `-UserOnly` is about *scope*, not privilege — it still needs an elevated
  session. It is deliberately not auto-elevated: if a standard user supplies a
  different admin's password, the policies would land in that admin's hive.
  For the same reason there is no pre-elevation HKCU cleanup in `-Uninstall`;
  one was added on review advice and could never have run, since the only
  process that would execute it is the unelevated one Windows refuses.
- **Windows writes to the registry, and that is durable.** `HKLM` and `HKCU`
  under `SOFTWARE\Policies\BraveSoftware\Brave` both survive `gpupdate /force`
  (verified 2026-10-20), so the macOS problem has no Windows equivalent.
  `-UserOnly` is about scope — this account rather than the machine — and is
  no less durable, but see below: it needs administrator rights all the same.
- **Every profile preference name is verified against `brave-core` before it
  is added.** A wrong name is completely silent: Chromium persists only prefs
  that differ from their default, so an invented key and a real key nobody has
  touched look identical in `Preferences`. Policies have `brave://policy` to
  catch a typo; preferences have nothing. Check the name in
  `brave/brave-core` — `gh search code '"the.pref.name" repo:brave/brave-core'`
  — and prefer the file that registers it, since names are retired and
  migrated (sponsored images moved from
  `brave.new_tab_page.show_branded_background_image` to
  `brave.brave_ads.sponsored.enabled` in 08/2026).
- **Policies are the primary layer; profile preferences cover only what has no
  policy** — mainly toolbar button visibility. Anything that can be done with
  a policy should be, because a policy removes the feature rather than hiding
  it.
- **New tab background photos are never touched.** Brave's own stock
  wallpapers are not ads, and the user wants them (stated 2026-10-20).
  `brave.new_tab_page.show_background_image` must never be written. The three
  *sponsored* wallpaper keys are ads and stay behind `--sponsored` /
  `-Sponsored`, opt-in.
- **Brave is quit before its preference files are touched, and given time to
  finish.** It rewrites `Preferences` and `Local State` on exit, so patching a
  running browser is pointless and killing it mid-write is how profiles get
  corrupted. Both scripts skip the step entirely when Brave is not running,
  then wait up to 10s and force only on a hang.
- **Preference files are written to a temp file and renamed.** Writing in
  place truncates the file before the new content exists, so a failure partway
  leaves nothing behind. Backups alone are not enough; the live file should
  never be in a broken state.
- **Backups are taken before the replace and pruned only after it succeeds.**
  Each run keeps `*.bak-initial` (the state before the first run, never
  touched) plus the two most recent timestamped copies. The copy of the
  current file must exist before it is overwritten, but deleting the oldest
  one is a separate step that waits for the replace: pruned first, a replace
  that fails (the file held open, immutable) still cost a backup, and a few
  failures in a row would swap every intermediate copy for clones of one
  unchanged file. A copy made for a replace that never happened is removed
  again. This was caught by running the failure on Windows, not by review: an
  earlier fix had moved the rotation after the temp-file write, which closed
  the failure *before* the write but not the one *at* the replace.
- **Shields, the ad blocker, auto-updates and sync are never touched.** The
  point is removing the storefront, not degrading the browser.

## Known traps

- **`PlistBuddy` wants `integer`, not `int`.** `Add :Key int 2` fails with
  *Unrecognized Type*. Under `set -euo pipefail` that aborts the whole script
  at the point of failure, and everything after it silently never runs. This
  cost a day: policies applied, profile preferences did not, and the output
  looked plausible.
- **Reading Brave's profile on macOS requires Full Disk Access.** Without it
  even `cat` on `Local State` fails with `Operation not permitted`, despite
  normal ownership and permissions. `sudo` does not help — TCC decides per
  *application*, not per user. The boundary is exactly at
  `~/Library/Application Support/BraveSoftware/Brave-Browser`; the parent
  directory reads fine.
  - The app that needs the grant is the one macOS holds responsible, which is
    not always the obvious one. In Claude Code, a terminal pane inherits the
    grant from `Claude.app`, but the agent's own Bash tool runs through
    `~/Library/Application Support/Claude/claude-code/<version>/claude.app`
    and needs its own entry — and that path changes with every update.
- **macOS cannot install a configuration profile from the command line.**
  `open`ing the `.mobileconfig` is as far as a script can go; the user then
  does Review → Install. Do not look for a `profiles install` route, it was
  removed for non-MDM use.
- **The policy is `IPFSEnabled`, not `BraveIPFSEnabled`.** The latter
  circulates in other debloat scripts and does nothing at all —
  `brave://policy` lists it as an unknown policy. A typo in a policy name is
  invisible unless that page is checked, since Brave ignores names it does not
  know.
- **Brave 155 marks five applied policies deprecated:** `IPFSEnabled`,
  `PromotionalTabsEnabled` and the three `PrivacySandbox*`. They still take
  effect and still matter on older builds, so they are kept deliberately.
- **PowerShell 5.1 has three sharp edges around Chromium JSON**, all of which
  were hit:
  - `ConvertTo-Json` defaults to `-Depth 2`; anything deeper is flattened into
    a string. `-Depth 100` is required.
  - `ConvertFrom-Json` throws on an empty-string key and on keys differing
    only in case, because it builds a `PSCustomObject`. Both measured on
    5.1.26100. The 2 MB limit widely cited alongside them is not real for
    reading — a 3 MB document parses. Three reviews in a row proposed
    rewriting this layer onto `JavaScriptSerializer` to escape all three;
    a scan of a real profile found zero occurrences of either construct, so
    the rewrite buys nothing and costs a second code path, since PowerShell 7
    has no `JavaScriptSerializer` and no such limitation either.
  - A UTF-8 BOM makes Chromium refuse the file. Write with
    `UTF8Encoding($false)`, not `Set-Content -Encoding UTF8`.
  - `[IO.File]::Replace($tmp, $path, $null)` throws *"the path is not of a
    legal form"*, and the method is not at fault. PowerShell binds `$null`
    to a .NET `String` parameter as an empty string, and `File.Replace`
    rejects an empty backup path. Verified 2026-10-20: the identical call
    with `[NullString]::Value` succeeds, so neither .NET Framework nor
    `[Environment]::CurrentDirectory` is involved. Either pass
    `[NullString]::Value` or, as here, use `Move-Item -Force` — a single
    rename on one volume, with no null to bind.
- **Local and CI `shellcheck` are different versions, and a clean local run
  is not a clean CI run.** A function that is only called indirectly, through
  `run`, is reported once as SC2329 by a new shellcheck and as SC2317 on every
  line of its body by an old one; the CI runner's is old. `tools/check.sh`
  disables both codes on those functions. The first push of it went red for
  exactly this reason, with 64 findings of the one code, after passing locally.
  The old version cannot be reproduced here, so a change to that kind of
  construct is confirmed by CI, not by the local run.
- **`shutil.copy2` copies a file's flags along with its contents.** A backup
  of an immutable `Preferences` (`chflags uchg`, which people set on purpose to
  stop Brave resetting settings) is itself immutable, so a plain `os.unlink`
  of it fails and was being swallowed: every failed run would have left a copy
  that could be neither pruned nor cleaned up. `remove()` in the macOS script
  clears the flag first. The Windows counterpart is the read-only attribute,
  which `Remove-Item -Force` already overrides.
- **Nothing in CI reads inside a quoted heredoc.** `bash -n` and `shellcheck`
  both skip the two embedded Python blocks, so a missing comma in `PROFILE`
  would pass every check and fail at run time. `tools/verify-keys.py` now runs
  `ast.parse` over them, which is why both blocks are `<<'PY'` heredocs rather
  than one of them being `python3 -c '…'`.
- **`set -o pipefail` plus `grep -q` is a trap**, and knowing it is not
  enough: it was documented here and then written again two rounds later, in
  the `--uninstall` path, where a Mac with enough profiles would have stopped
  opening the Profiles pane. Both callers now go through one `profile_installed`
  helper that captures the output first. `grep -q` exits at the
  first match, the producer takes `SIGPIPE`, and the pipeline reports 141 —
  so a successful search reads as a failure. It bit `profile_is_current`,
  where it would have meant "profile not installed" on any Mac with enough
  configuration profiles to fill the pipe buffer. Capture the output into a
  variable and match on that instead; `grep >/dev/null` is not a reliable fix.
- **Never run the macOS script with `sudo`.** It needs no root, and under it
  `os.replace` leaves `Preferences` owned by `root` — `shutil.copymode` copies
  the mode, not the owner — after which Brave cannot read its own profile,
  while `defaults write` goes to `/var/root`. The script refuses to start as
  root for this reason.
- **`$0` is not a path when the script is piped.** Three separate reviews have
  reported that `curl … | sh` puts `/bin/sh` in `$0`, so `[ -r "$0" ]` passes
  and `--help` would `sed` a binary. It does not: `$0` is the bare word `sh`,
  `zsh` or `bash` in every piped form, including `sh < file`, and the guard
  short-circuits. Verified three times; do not "fix" it again.
- **Keep the PowerShell script's printable strings ASCII.** It is stored
  without a BOM, and Windows PowerShell 5.1 then reads a `.ps1` as the system
  ANSI code page rather than UTF-8, so a typographic dash in a message prints
  as mojibake. Comments are harmless, since nobody sees them; `verify-keys.py`
  enforces the rule for everything else. Adding a BOM would fix the display
  but is its own trap — anything that concatenates or pipes the file then
  carries the marker into the middle of the text.
- **`exit` inside `irm … | iex` closes the user's console.** `Invoke-Expression`
  runs the code in the caller's own scope, so `exit` behaves exactly as if it
  had been typed at the prompt. The refusal paths that are reachable only when
  piped therefore end with `throw`, which stops the run without taking the
  window with it — `exit` is used only when `$PSCommandPath` says a file is
  running. The four lines of `CategoryInfo` noise `throw` leaves behind are a
  deliberate trade: routing a flag back to the top level to allow a clean
  `return` would mean touching a path that can only be tested by hand, and
  the two previous cosmetic passes over this code each produced a regression.
- **A PowerShell parameter set is resolved at invocation, not at parse
  time.** `Split-Path -LiteralPath $p -Leaf` parses cleanly and fails at run
  time with "parameter set cannot be resolved", because 5.1 keeps
  `-LiteralPath` and `-Leaf` in different sets. The syntax check that catches
  everything else cannot catch this, and it broke every profile patch for one
  commit. Prefer `[IO.Path]::GetDirectoryName` / `GetFileName`.
- **`raw.githubusercontent.com` caches branch URLs for minutes.** After a push,
  a one-line install can still fetch the previous version — this produced a
  bug report for code that had already been fixed. To test a fresh commit, use
  a URL pinned to its SHA.

## Incidents

- **2026-09-15** — the script had been "resetting" for weeks. Two causes, one
  masking the other: the `int`/`integer` abort above, and then Full Disk
  Access blocking the profile patch. The profile-preferences step had in fact
  never run successfully.
- **2026-09-16** — all policies gone after a reboot: `/Library/Managed
  Preferences/` had been removed by macOS, directory and all. This produced
  the configuration-profile design.
- **2026-10-20** — the fix for a code-review finding (non-atomic writes) broke
  profile patching outright on Windows, via `[IO.File]::Replace`. The output
  said `skipped`, which reads as harmless; it was caught only by checking an
  actual preference value after the run. Verify effects, not exit status.
- **2026-10-20** — a third review found that the fix for the previous entry
  was itself unsound: verifying names with `gh search code` produced two more
  fictional keys (`brave.today.enabled`, see the rule above) and deleted a
  real one. It also caught that the atomic-write change had been dropping
  `Preferences` from Brave's `0600` to a world-readable `0644`, since
  `os.replace` carries the temp file's mode. Two rounds of "verification"
  before anything was actually verified.
- **2026-10-20** — a second review found that most of the profile preference
  layer was writing key names that do not exist in `brave-core` — inherited
  from the script this project grew out of and never checked, including every
  key behind `--sponsored`, the daily-ping key (`brave.stats.ping_enabled`
  instead of `brave.stats.reporting_enabled`) and Web Discovery
  (`brave.web_discovery.enabled` instead of `brave.web_discovery_enabled`).
  They had been "verified" by seeding them and watching the script rewrite
  them, which tests nothing. The policy layer was unaffected and had been
  genuinely verified, because `brave://policy` reports names it does not
  recognise. Preferences offer no such signal, hence the rule above.
- **2026-10-20** — the pre-elevation `HKCU` clean added in a later round ran
  unconditionally, which produces the same symptom as the incident below and
  has been mistaken for its cause twice. It cannot be: that code did not exist
  yet when the values disappeared.
- **2026-10-20** — 26 values vanished from `HKCU` between being written and
  being removed, with nothing in either script touching that hive in between.
  Cause never established. `gpupdate /force` was tested and ruled out. If it
  recurs, this is the open thread.

## Testing

**`tools/check.sh` runs everything that can run on the current machine** — bash
syntax, shellcheck, PowerShell parsing, the bundled profile, `verify-keys.py`,
and a smoke run of the macOS script with every system-touching command stubbed.
It is the one command to run before pushing, and the one the reviewer is told
to run. A check that cannot run prints `SKIP` with the reason; that is not a
pass. CI covers shellcheck and PowerShell parsing (which need `shellcheck` and
`pwsh` installed locally), but it does **not** run the smoke run, which needs
macOS. It needs network, because `verify-keys.py` reads brave-core.

The smoke run exists because the manual version of it — stubs on `PATH`,
`HOME` and `TMPDIR` redirected — was being rebuilt by hand every round. It also
compares the profile the script generates against the one committed, which
`verify-keys.py` only does textually.

**It seeds a stand-in Brave profile, and must.** For a while it did not, and
the script just printed "profile not found" and skipped the entire
preference-patching step — the largest embedded Python block — while the
comments claimed the run exercised everything. A smoke run that never reaches
the code says nothing about it. The seeded profile is checked by outcome on
the files (values set, unrelated data kept, the original's mode kept, `0640`
here on purpose so that only a real copy can pass, `.bak-initial` equal to the
original, rotation after a second run, `ads_service` gone). Two further
profiles are made to fail on purpose, to prove what the success path cannot
show. One has a dangling symlink where its backup must go, so the patch dies
after the temp file exists: the file is removed in `finally`, and one
profile's failure does not stop the others. The other is made immutable with
two old backups already beside it, so the final replace is refused: the backups
must come out exactly as they went in. That cleanup was once lost without
anyone noticing; each of these checks was verified by breaking the script and
watching the run fail.

`tools/verify-keys.py` checks every preference and policy name against
brave-core, that the two scripts agree on names *and values* and on which file
each pref goes to, that no pref appears in two groups at once, and that the
bundled `.mobileconfig` has not drifted from the policy list in the shell
script. Comparing names alone was not enough — it passed a key that only one
platform set. CI
runs it on every push and weekly, since Brave retires names over time. Run it
before touching either key list — it catches exactly the class of bug that got
through three reviews. It also refuses to skip a line it cannot parse: a
regex that silently ignores a malformed entry reproduces the very problem
it was written to catch.

Behaviour is still only verified by running the scripts.

PowerShell cannot be run on macOS, so Windows changes are written blind and
must be exercised on a real machine.

Confirm every edit actually landed, and confirm it by reading the file rather
than by trusting the tool that made it. Work has been lost that way three
times. Twice a search-and-replace matched nothing, because the file used
typographic dashes where the pattern assumed hyphens — the file is kept
strictly ASCII now, enforced by `verify-keys.py`, though for the encoding
reason above rather than this one. The third time a batch of five edits saved
only at the end, so an assertion on the last discarded the four that had
succeeded, and the commit message went on to list fixes that were not in the
commit. That is worse than missing them: it is a false record, and the next
review is what caught it.

- **macOS** — run in a sandbox with `open`, `osascript`, `pkill`,
  `system_profiler` and `defaults` stubbed on `PATH`, with `HOME` and `TMPDIR` redirected. That
  exercises everything except the manual profile install. Check the generated
  `.mobileconfig` with `plutil -lint` and count the policies in it.
- **Windows** — parse first, which is the equivalent of `bash -n` and catches
  what cannot be caught on the Mac:
  ```powershell
  $e = $null
  [System.Management.Automation.Language.Parser]::ParseFile($path, [ref]$null, [ref]$e) | Out-Null
  if ($e) { $e | % { "line $($_.Extent.StartLineNumber): $($_.Message)" } } else { 'syntax OK' }
  ```
  Then verify behaviour, not output: read a patched preference value back,
  count registry values, and confirm `-Uninstall` leaves foreign policies
  alone by planting one first.
- `-Sponsored` passing through UAC can only be tested from a *non-elevated*
  console, with the sponsored keys seeded to `true` beforehand — otherwise a
  dropped flag and a working one look identical. Note what that test does
  *not* show: seeding a key and watching the script overwrite it proves the
  flag arrived, never that the key is one Brave reads. Only the source
  settles that.

## Not verified

What no check or run has covered, so that nobody mistakes silence for a pass.

- `-DataDirOverride` with a separate administrator account: needs two accounts,
  never run. The parameter is accepted by name; the scenario it exists for is
  not exercised.
- The `$BraveAlive` path (Brave still running after the forced kill): cannot be
  provoked on demand.
- The `ads_service` cleanup counter: no such directory exists on any machine
  tried, so the branch has never executed.
- PowerShell 7: only Windows PowerShell 5.1 has been run.
- The macOS smoke run is not in CI (it needs macOS); CI runs shellcheck and
  PowerShell parsing, which a plain local run skips when the tools are absent.
- Backup pruning after a successful replace on Windows (commit `542e67b`): the
  macOS side is covered by the smoke run, the Windows side has not been run
  since the change.
